# 决策日志（Decision Log）

> 面试时"为什么这么做"的答案都在这里。按时间倒序。

## 2026-09-04（深夜）· 实测数据轮

**D18 精确性定理 vs GPU 浮点现实（今晚最有价值的发现）**
投机解码单测证明"输出 == target 纯贪心"（CPU 精确算术下 3 种子全过），
但真机 bf16 上 k=4 出现 exact=False——排查确认：整批 teacher-forcing 验证
前向与逐 token 基线前向在 bf16 下存在位级差异，近平局处 argmax 翻转后
混沌放大（同 bf16 的 k=8 反而 exact=True）。**fp32 重跑 exact=True 且加速
反而更好（1.41×→1.96×）**——假设被实验证实。教训分层：①定理是关于分布
的，GPU 加了浮点现实这一层；②"真机失败+假设+对照实验证实"是完整科学
闭环，比一次通过有价值得多；③对精度敏感的比较（argmax 逐位对照）应在
fp32 或设计容差下进行。

**D19 朴素投机解码的速度结构与公式校验**
实测 tok/target-fwd = α·k + 1（k=4: 0.899×4+1=4.59≈4.57 ✓；k=8: 0.799×8+1=7.39≈7.31 ✓）
——贪心验证下每步产出 = 接受数 + 1（修正或红利），与采样版的
(1-α^(k+1))/(1-α) 公式不同（那是"全接受概率"视角的期望推导口径差异，
面试可讲）。k=8 加速 0.97×<1：无 KV cache 的朴素实现被每前向固定开销支配
（spec 每步 k+1 次前向 vs 基线 1 次），真正的加速比必须在 KV cache 实现
下测——已列为 roadmap，不假装这个数是部署口径。

**D20 SmoothQuant 复现成功且 α 意外地"高而稳"**
两模型最优 α 同为 0.7（0.5B 3.65× / 1.5B 3.98× 提升）。文献常用 0.5；
最优值随模型/任务变化，网格搜索本身就是答案的一部分——这正是"α 是
跷跷板"的实证：给固定 0.5 不如给搜索。

## 2026-09-04（晚）· V2.1 加厚轮

**D16 实现与理论矛盾时，先核对调用契约**
SmoothQuant 有效性测试连续失败，我先构造了一套"离群通道主导信号时平滑有害"
的边界条件理论来解释数据——后来发现是测试调用 `smooth_scale` 时把
(w_max, act_max) 两个参数传反了，s 整个倒置。库是对的，理论是空中楼阁。
教训：**单元测试的意义在于暴露不一致，而"解释失败"必须从调用契约、
数据形状这些机械性错误查起，理论解释是最后的手段**。签名设计上，
(w_max, act_max) 这种易混参数序也是坑源——后续 API 一律 (weights, activations)。

**D17 为什么补 SmoothQuant 与投机解码（而不只做 weight-only）？**
字节 Seed 岗位 JD 原文含"解码加速/投机解码"，且真实部署是 W8A8/激活量化的
世界——weight-only 故事再完整也缺一半。两者都可从零实现且可离线单测：
SmoothQuant 的等价变换与 α 跷跷板是推导级考点；投机解码的贪心验证
"输出分布不变"是可测试的定理。W8A8 的损失必须按 batch 蒙特卡洛
（激活误差依赖具体 token），不能复用 H 的 trace 闭式——这个口径区别
本身就是面试细节分。

## 2026-09-04 · V2 统一预算分配日

**D12 为什么损失用 tr(ΔW·H·ΔWᵀ) 作为统一货币？**
剪枝文献（OBS/SparseGPT）与量化文献（GPTQ）其实共用同一个目标——校准集输出
L2——但各自论文用各自形式呈现，跨方法族比较历来不公平。H = XᵀX 只依赖输入
分布，与压缩方法无关：一次采集，全部菜单选项共用。损失计算无需保留 X
（trace 公式），内存可控。**验证**：trace 恒等式单测（float64 下 1e-10 相对偏差）。
数值教训：恒等式验证必须 float64——float32 的累积误差在 1e-6 量级，
曾让该测试假阴性。

**D13 为什么分配用精确 DP 而不是（文献常用的）敏感度启发式？**
菜单比特值离散且全模型共享 → 分离式背包可 DP 精确求解。实现要点：预算按
平均比特计（Σ d_l·b_l ≤ target·Σd_l），维度按 GCD 缩放控制状态数
（0.5B@0.25bit ≈ 数万状态，秒级）；状态数超限自动降粒度、最终回退贪心。
对照策略：贪心（边际价值升级）与 uniform。**首个发现（合成损失表）**：
修正方向后的贪心与 DP 完全打平——菜单结构可能"贪心友好"（近凸），真实
损失表上是否成立是 V2 实跑要回答的问题之一；若成立，"精确 DP 的价值 = 
正确性锚点 + 非凸场景保险"仍是站得住的叙事。

**D14 烟雾测试抓到的两个设计 bug（自动化验证的价值证明）**
①DP achieved_bits 恒为 0：回溯时位置变量被循环内自减污染——先捕获终点
再回溯；②贪心方向反了：从最省比特起点出发却只在"超出预算"时动作，目标
高于最省平均比特时永远不触发，返回全场最差点——重写为"从最省可行点出发
按边际价值升级"。两个 bug 都不是单测能轻易暴露的端到端语义错误——
**合成数据端到端烟雾 + 常识断言（bits 必须接近 target）是第三道防线**。

**D15 同类错误三次：__init__.py 导出遗漏**
write_csv（v0.1）、plot_allocation_map（V2）——两次 ImportError 都发生在
"模块写完、忘了更新包导出"的同一环节。已固化习惯：新增公共函数时同步
三处（模块、__init__、调用方 import）。

## 2026-09-03（深夜）· v0.2 深化轮

**D8 为什么自研 OBC/GPTQ 而不是只用 Wanda + 库版 GPTQ？**
面试高频题"GPTQ 对 RTN 改进了什么/SparseGPT 和 Wanda 差别"背答案是空的；
自己实现后：①自研 GPTQ W4g128 = 14.13 vs RTN 15.69（0.5B），误差反馈的收益
是自己的数字；②实现过程暴露了静态/动态掩码的本质区别（见 D9）。

**D9 静态掩码失败与动态重评分的翻身（本项目最完整的方法学故事）**
第一版 OBC 用"静态预选掩码 + 顺序补偿"：mask 按 w²/(H⁻¹)_jj 一次性选定。
0.5B 上 PPL 54.2，比 Wanda 的 25.5 还差。机理：H⁻¹ 对角打分会集中删除
"被其他列强保护的列簇"，但簇内保护者彼此删除后保护失效——单列理论损失
严重低估联合删除的实际损失，稀疏度越高越崩（1.5B 上 13.7 vs Wanda 13.3，
0.5B 上彻底崩）。
**修复**：实现 SparseGPT 忠实版块级动态重评分（`--obc-mask dynamic`）——
处理到每个 block 时用当前已补偿的权重重新定删留。结果反转并反超：
0.5B **17.52**（vs Wanda 25.52，好 31%）、1.5B **11.67**（vs 13.34）——
全矩阵 50% 稀疏度最优。教训与方法论：**顺序方法的删留决定必须跟着补偿
动态走**；"复现论文的失败模式 → 定位机理 → 按论文修正 → 反超"是比
一次跑通强得多的面试故事。

**D10 SGMix 负结果及其解释（诚实记录）**
敏感度引导的混合稀疏（OBS 干跑损失 → 反比分配）在 0.5B 上 PPL 29.5/35.0，
均差于均匀 25.5。两个原因：①OBS 干跑敏感度度量的是"OBS 打分+补偿"下的
损失，迁移不到"Wanda 打分+无补偿"的实际上 pruning；②稀疏度-损失曲线强凸
（25%→+0.5，50%→+12.3，60%→+63.5），把鲁棒层推过 50% 的超线性惩罚吞掉了
敏感层降配的收益。**改进方向已注明：用 Wanda 自身 score 的干跑损失 + 凸性
感知预算**。负结果如实入库——面试里"你试过什么没用的方案"比全是成功更可信。

**D11 合成测试的隐含前提**
OBC 补偿有效性测试最初用 iid 随机 X——Hessian 近对角、列间无相关性，
补偿量≈0，测不出算法价值（且曾因评估函数漏减参考输出而误报失败）。
修正：激活必须带相关性（X = randn @ Aᵀ），评估必须是重构误差
||XW−XW_ref||²。教训：**合成测试的分布假设要匹配算法发挥作用的前提**。

## 2026-09-03 · 初始设计

**D1 为什么第一个项目做压缩工具箱而不是微调/RL项目？**
差异化：求职市场上 RAG/微调 demo 严重同质化，而"压缩率-质量-速度"完整
trade-off 证据链稀缺；且与本人剪枝方向的论文形成互文（工具箱本身方法无关，
但作者懂这个领域的痛点）。

**D2 为什么剪枝评测用稠密推理口径？**
官方 Wanda 论文的 PPL 评估同样是稠密权重置零口径。诚实声明比伪装加速
更有面试价值：混用"方法学质量"与"系统加速"口径是此类项目的典型注水点。

**D3 为什么 RTN 自己写而 GPTQ/AWQ 用库？**
RTN 是面试高频推导题，从零实现是理解证明；GPTQ/AWQ 的价值在工程打包与
内核生态，自研无增量价值——"自己写该写的，封装成熟的"是工程判断力的体现。

**D4 为什么 CLI 而不是 Web UI？**
目标用户是跑实验的人（自己+面试官复现），CLI + JSON schema + 一键报告
是实验工具的正确形态；Web UI 属于"看起来完整"的表演性功能。

**D5 为什么测试用 mock tokenizer + 微型模型？**
测试的价值在"每次改动后 10 秒内告诉我有没有坏"，不在覆盖真实模型怪癖；
真实模型冒烟由 scripts/run_smoke.sh 承担（一次 ~10 分钟）。

**D6 论文方法为什么不进仓库？**
未发表工作保护。仓库内以 BasePruner 可插拔接口预留位置；面试时口头说明
"我的剪枝方法以私有插件形式接入了同一评测管线"。
