# LiteForge V2 设计：压缩预算的统一分配（Unified Compression Budgeting）

> 状态：设计定稿 2026-09-04。V1（方法实现与评测管线）已完成，见 README/EXPERIMENT_PLAN。
> 本文回答 V1 的遗留问题：*"实现已发表方法 ≠ 有竞争力的项目——缺一个自己的研究问题。"*

## 0. 研究问题（一句话）

> **给定"把模型压到 X%"的预算，逐层应该花在剪枝还是量化上？——用同一损失度量计价，搜索比均匀分配更优的逐层策略。**

动机：部署团队每天都在做这个决策（显存不够，先剪还是先量化？），但剪枝文献
（Wanda/SparseGPT）和量化文献（GPTQ/AWQ）各说各话，损失度量互不可比。
本仓库的架构恰好提供了统一的基础：**OBC 剪枝与 GPTQ 量化共享同一个 Hessian
引擎**——两者的期望输出损失都能用校准集 L2（H = 2E[xxᵀ]）计价。

## 1. 三个柱子

### ① 统一预算分配（原创核心）

**损失计价**：对每个 Linear 层 l，
- 量化的期望损失：GPTQ 顺序量化后 `||XW - XW_q||²`（直接可测，复用 quantize_ 的备份机制）；
- 剪枝的期望损失：OBC 动态重评分剪枝后同法可测（或用 OBS 干跑损失做快估计）。

**分配器**（先简后繁，逐级消融）：
- L0 基线：全量化 W4（= V1 已有的 GPTQ 行）；
- L1 贪心：给定混合目标比特（如 2.5 bit/权重），按"每省 1 bit 的损失代价"对
  层排序，代价低的层先降（W4→W3 或→剪枝 25%/50%）；
- L2 迭代修正：分配后实测各层损失，重新排序一轮（预算再平衡）。

**评测**：0.5B/1.5B/3B × 目标 {2.75, 2.5, 2.25} bit，对照 L0 与均匀混合。
产出：分配策略可视化（哪些层被剪、哪些层被量化到 W3）+ PPL 对照表。
**任何结果都可写**：找到更优分配 = 正结果；证明"全量化已近最优" =
同样有价值的负结果（部署含义直接：别折腾混合精度）。

### ② 能力损失地图（分析层）

PPL 之外补下游：lm-eval 接入 MMLU 子集（STEM/人文/社科分桶）、GSM8K、
HumanEval（可选）。对 {dense, W4, W3, 剪 50%, 混合} 各测一遍。
回答："**压缩最先失去什么能力？**"——PPL 几乎不动但数学崩了？还是均匀退化？
这是部署团队真实的上线决策依据，也是面试官天天面对的问题。

### ③ 部署成本闭环（系统层）

vLLM 实测（WSL2 或实验室 Linux）：dense / GPTQ-W4 / ①的混合模型，
压测吞吐、TTFT、显存（deploy/vllm_bench.py 已就绪）。
换算成**每百万 token 成本**，与②的能力损失并排成一张图——
"压缩率-质量-成本"三角闭环，V1 的诚实口径（速度单独实测）在此兑现。

## 2. 执行排期（用户论文截稿后，2-3 周穿插）

| 周 | 内容 | GPU 量 |
|---|---|---|
| W1 | ① 损失计价器实现 + L1 贪心分配器 + 0.5B 验证 | 挂机批 ~4h |
| W2 | ① 3 模型 × 3 目标全矩阵 + L2 迭代；② lm-eval 接入 | 挂机批 ~8h |
| W3 | ③ vLLM 实测（需 WSL2/Linux 环境）；博客《压缩预算该花在哪》；简历更新 | ~3h |

## 3. 与 V1 的关系

- V1 的所有方法/评测/口径纪律原样保留，V2 是在其上的"研究层"；
- Hessian 引擎、统一 schema、report 聚合器直接复用——V1 的架构投资在此兑现；
- 新增模块规划：`liteforge/allocate.py`（分配器）、`liteforge/lossmeter.py`
  （统一损失计价）、`eval/lmeval_adapter.py`（②的接入）。

## 4. 风险

| 风险 | 对策 |
|---|---|
| 混合分配赢不了全量化 | 负结果同样是产出（部署含义明确）；博客照样写 |
| lm-eval 依赖重/Windows 不友好 | 评测放实验室 Linux 或 WSL2；或手写 MMLU 子集评测（数据 CC 协议可下载） |
| vLLM Windows 不可用 | WSL2 或实验室机器；deploy/vllm_bench.py 是纯标准库客户端，哪里有服务哪里跑 |
